## Scope and evidence

Read `CLAUDE.md` and `README.md` first. Only this report was authored. Source, tests, configuration, lockfiles, and the two existing CODEX analysis reports were left unchanged. These are proposed product behaviors, not implemented features or additional bug findings. Priorities reflect the value and implementation scope visible in this repository, rather than measured user demand. S means a localized addition; M means a bounded change across several existing components; L means a substantial feature. No recommendation requires a full rearchitecture.

The production modules were already read in the preceding reviews at this unchanged commit. This pass revisited feature-relevant paths module by module:

Existing tests use helper programs for lifecycle behavior; they do not prove deployment-specific behavior. Historical planning documents were not treated as evidence of current implementation.

A targeted search for `TODO`, `FIXME`, `todo!(`, and `unimplemented!(` in `src/` and `nix/` returned no matches. The `stub` matches in `launch.rs` are test doubles, not abandoned production functionality. No unused field or dead route was established as evidence of an unfinished feature. The recommendations below therefore extend implemented capabilities or address a documented interaction limitation.

External API reference: the project uses GIO 0.22 and already resolves desktop applications. GIO provides [registered application discovery](https://docs.gtk.org/gio/type_func.AppInfo.get_all.html); that list requires [menu-visibility filtering](https://docs.gtk.org/gio/method.AppInfo.should_show.html). This supports FEAT-04 without introducing a new discovery service.

### FEAT-01 — Tile editing reachable with ordinary remote presses

**Priority:** high. **Effort:** M.

**Natural fit:** [src/window.rs:1212](C:/Projects/VexTheater/src/window.rs:1212) lines 1212–1264, 1843–1881, 2245–2289; `Page::TileOptions`, `options_for`, `Command::Move`, `Command::Remove`, and reset/remove confirmations. [README.md:132](C:/Projects/VexTheater/README.md:132) describes the CEC bridge's press/release behavior and absent Menu key.

**Current evidence:** `arrange_key()` opens tile options through Menu/F2, while held Enter and right-click are the other entry points. Ordinary Select/OK already maps to Enter. The Move/Remove page and cancel-first confirmations are implemented, but the documented CEC remote cannot invoke their entry gesture. Reset order likewise requires held Back.

**Concrete behavior:** Add a focusable **Manage tiles** entry reachable from the main header using arrows and OK. It offers the main page and configured submenu pages as editing targets. Choosing a tile opens its existing options instead of launching it; Move returns to that tile's original grid with the tile picked up. Provide **Reset tile order** in the same management flow, using the existing confirmation. Back exits management and returns focus to its opener. Keep ordinary tile activation unchanged outside management.

**Why this priority:** It makes already-built personalization usable with the remote described in the README. The work is primarily an alternate navigation path, not a new ordering or persistence system.

**Acceptance checks:** Using only arrows, OK, and Back, move and remove a main-page tile and a submenu tile, restore one through Add, and reach/cancel reset. Verify that selecting an edit target never launches its app and that focus returns to the intended tile/page.

### FEAT-02 — Pending-launch status and cancellation

**Priority:** high. **Effort:** S.

**Natural fit:** [src/window.rs:423](C:/Projects/VexTheater/src/window.rs:423) lines 423–463 and 1741–1793; `Request::{Tile, Home, Desktop}` and `CloseQueue`. [src/launch.rs:257](C:/Projects/VexTheater/src/launch.rs:257) lines 257–264 documents the close-time budget.

**Current evidence:** A tile request enters `close_then()`, waits for `stop_all()`, then acts on the latest queued request. Feedback in this path is currently emitted for errors after the wait. Closing can take about 20 seconds, and successive choices replace the pending tile.

**Concrete behavior:** While the queue is busy, show a persistent status such as **Closing previous app… Next: Netflix**, with a focusable **Cancel launch** action. Choosing another tile updates the displayed destination immediately. Cancel replaces the pending tile with `Request::Home`; the existing close finishes normally and no replacement app starts. Clear the status on every completion/error path. Use an indeterminate indicator rather than a percentage, since the close code does not expose measurable progress.

**Why this priority:** A small addition exposes state already tracked by the queue and explains otherwise silent delays. Cancellation can reuse Home's existing meaning without interrupting process cleanup or sending additional signals.

**Acceptance checks:** During a deliberately slow close, choose A then B and verify only B is named and launched. Cancel B and verify cleanup completes but neither app starts. Unknown-scope and timeout outcomes must clear or replace the status rather than leave it spinning.

### FEAT-03 — Setup and health page on the TV

**Priority:** high. **Effort:** M.

**Natural fit:** [src/diagnose.rs:14](C:/Projects/VexTheater/src/diagnose.rs:14) lines 14–88, 151–177, 229–243; `Check { what, outcome }`. [src/window.rs:237](C:/Projects/VexTheater/src/window.rs:237) lines 237–242, 1584–1627, 2395–2401; [src/webapp.rs:39](C:/Projects/VexTheater/src/webapp.rs:39) lines 39–60; [src/keybinding.rs:67](C:/Projects/VexTheater/src/keybinding.rs:67) lines 67–99.

**Current evidence:** `--diagnose` already checks GNOME schemas, data directories, systemd helpers, config, Flatpak availability, and referenced files, but renders only terminal text. The UI separately knows whether apps/browser are missing. An empty main page currently points users to Add. Home-key configuration is owned by the generated config and synchronized into GNOME.

**Concrete behavior:** Offer **Setup & health** from the header and empty-state screen. Show separate, refreshable results for session helpers, configuration, configured Home shortcut, browser availability, and missing tile apps. Include actions to open Add or retry config loading, and show the active config path and concise failure reason when repair requires changing configuration. A remote user should be able to discover that catalog apps need a browser without opening a terminal. Read actual shortcut state for diagnosis without silently rewriting it from this page.

**Bounded implementation:** Reuse structured checks and their plain-text renderer for the CLI; add a UI renderer and the missing browser/shortcut checks. Run helper checks asynchronously or off the UI thread: the present synchronous runner sleeps while polling and permits five seconds per command. Keep settings ownership in the existing Nix/config path instead of introducing a conflicting settings editor.

**Why this priority:** Session environment and missing application problems already have dedicated code and extensive README troubleshooting. Exposing that information where the app is used removes a concrete support barrier.

**Acceptance checks:** Missing browser, missing schema, bad config, and absent Home shortcut each produce a distinct explanation; Refresh clears resolved failures. A hanging helper must not block Back or navigation. CLI and UI should agree on the same underlying check result.

### FEAT-04 — Add installed desktop applications from the launcher

**Priority:** medium. **Effort:** M.

**Natural fit:** [src/tiles.rs:18](C:/Projects/VexTheater/src/tiles.rs:18) lines 18–24, 99–116, 165–200; `Shown`, `Item`, and `Addable`. [src/window.rs:1951](C:/Projects/VexTheater/src/window.rs:1951) lines 1951–2032, 2378–2391; [src/launch.rs:115](C:/Projects/VexTheater/src/launch.rs:115) lines 115–124 and 134–138.

**Current evidence:** Add offers hidden configured tiles and fixed catalog services only. Desktop-file actions already resolve names/icons, check installation, and launch through the existing scope or Flatpak path. A user can configure an installed app in JSON but cannot add that app from the TV.

**Concrete behavior:** Add an **Installed applications** section populated from registered desktop entries visible in application menus. Choosing an app adds its desktop ID to user state and selects its new main-page tile. Reuse desktop metadata for name/icon and the existing `Action::Desktop` launch path. If that desktop ID already has a visible tile, focus it; if it is hidden, offer to restore it. Include Flatpak desktop exports that GIO can discover, while explaining missing discovery through FEAT-03 rather than promising to enumerate every installation.

**Model change:** Add a defaulted desktop-ID collection beside `Shown.added`; keep current catalog IDs intact. Extend the listing/add/remove mappings, with compatibility tests for existing `tiles.json` files. This changes user state, not the generated `Config` schema, and does not require a package installer.

**Why this priority:** Most of the launch behavior exists, but discovery, persistence, duplicate handling, and UI wiring make it more than a small addition. Resolve the desktop metadata argument issue documented as BUG-06 in [CODEX_ANALYSIS_BUGS.md](C:/Projects/VexTheater/CODEX_ANALYSIS_BUGS.md) as part of validating the expanded desktop-app surface.

**Acceptance checks:** Add a desktop app, restart, move/remove/restore it, and verify persistence. Exclude menu-hidden entries, avoid duplicate desktop IDs, and show an unavailable state if the application is later uninstalled. Test desktop entries with metadata field codes as well as simple Exec lines.

### FEAT-05 — Export and restore the user's tile layout

**Priority:** medium. **Effort:** M.

**Natural fit:** [src/tiles.rs:18](C:/Projects/VexTheater/src/tiles.rs:18) lines 18–45; [src/order.rs:10](C:/Projects/VexTheater/src/order.rs:10) lines 10–29; [src/files.rs:20](C:/Projects/VexTheater/src/files.rs:20) lines 20–23 and 52–76; [src/main.rs:26](C:/Projects/VexTheater/src/main.rs:26) lines 26–40; [src/window.rs:283](C:/Projects/VexTheater/src/window.rs:283) lines 283–304.

**Current evidence:** Personalization already consists of serializable `Shown` and `order::Saved` values in two small state files. The display-free `--print-order` path combines them with config to show the effective layout. There is no export/import command in the current CLI dispatch.

**Concrete behavior:** Provide a display-free export command that produces a versioned layout bundle containing added catalog IDs, hidden tile identities, per-page ordering, and the source page/identity inventory used to detect mismatches. A restore-preview command reports the resulting layout plus unmatched pages, names, occurrences, or catalog IDs. Explicit apply restores the validated personalization, preserving a recoverable previous snapshot if saving fails. Reject unsupported formats and malformed identities before changing either live state file.

**Scope:** This is layout portability, not a machine-state backup. Exclude GNOME recovery snapshots, runtime PIDs/mode, browser profiles/cookies, and generated system configuration. Run apply through the owning launcher or require it to be stopped, so its in-memory state cannot overwrite the restored files. Individual atomic writes do not make the two-file restore a transaction; the implementation must handle partial failure explicitly.

**Why this priority:** It enables reinstall/migration of the layout using existing small models. Validation and coordinated restore make effort M, while a first export-only increment can be S.

**Acceptance checks:** Export → preview → restore produces the same effective `order_listing`, including duplicate names and hidden tiles. A changed config reports unmatched identities rather than selecting another same-named tile silently. Inject failure on the second save and verify a documented recovery path preserves the old layout.

### FEAT-06 — Launch an existing tile through the forwarded CLI

**Priority:** medium. **Effort:** M.

**Natural fit:** [src/main.rs:47](C:/Projects/VexTheater/src/main.rs:47) lines 47–61; [src/window.rs:198](C:/Projects/VexTheater/src/window.rs:198) lines 198–275, 1648–1709, 1741–1793; [src/order.rs:10](C:/Projects/VexTheater/src/order.rs:10) lines 10–15. Existing `HANDLES_COMMAND_LINE`, `Page` keys, tile identities, and the close queue supply the integration points.

**Current evidence:** Commands such as `--home`, `--desktop`, and `--reload` already reach the running GUI instance. App launches, however, are reached through tile activation. The same dispatcher already performs installation checks before closing an existing app and serializes replacement launches.

**Concrete behavior:** Add a command such as `--launch <page-key> <tile-name> <occurrence>` and a machine-readable tile listing that provides those selectors. Resolve only visible, existing app tiles against the current config/user layout, then use the same availability checks, origin tracking, webapp preparation, and close queue as a click. This lets a spare remote button, desktop shortcut, or local automation launch a chosen service without duplicating shell/browser commands outside VexTheater.

**Boundaries:** Return an error for a stale selector, hidden tile, submenu, or power action. Use the current page/name/occurrence convention explicitly; do not claim selectors survive renaming or reordering same-named configured tiles. CLI success means the request was accepted, with later launch failures reported by the existing UI/log path. This adds no network listener or general-purpose remote command executor.

**Why this priority:** The single-instance command channel and lifecycle queue already exist. Selection semantics and ensuring parity with click behavior account for the moderate effort.

**Acceptance checks:** A command sent to an already running instance launches the selected tile once. Two rapid requests obey latest-request-wins. A missing app or invalid selector leaves the existing app running. Builtin shutdown/restart cannot bypass their confirmations through this command.

### FEAT-07 — Browse and filter visible tiles across submenus

**Priority:** low. **Effort:** M.

**Natural fit:** [src/config.rs:30](C:/Projects/VexTheater/src/config.rs:30) lines 30–49 and 187–206; [src/tiles.rs:123](C:/Projects/VexTheater/src/tiles.rs:123) lines 123–134; [src/window.rs:68](C:/Projects/VexTheater/src/window.rs:68) lines 68–85, 1648–1709, 2321–2373; [src/grid.rs:29](C:/Projects/VexTheater/src/grid.rs:29) lines 29–55.

**Current evidence:** Config supports named submenus, and entries already carry names, descriptions, icons, and actions. The grid shrinks tiles as the count grows. Existing visibility/order helpers distinguish visible tiles from hidden preferences, but there is no search/filter page in `Page` or the input routes.

**Concrete behavior:** Offer **Browse all** with app tiles grouped or labeled by their page. Filter by tile name and description using keyboard text, with an alphabet-group picker usable through arrows/OK for remote users. Include only tiles reachable through visible submenu links, retain distinct entries for duplicate names, and show their page label. Activating a result uses the original tile identity and launch path; Back returns to the prior page/focus. Filtering never changes saved order or unhides tiles.

**Bounded implementation:** Build the result set from existing entries and `tiles::visible`, using a visited-page set to handle submenu cycles. Search local tile metadata only. Preserve source page/identity in results so command dispatch and return-to-origin behavior do not depend on the temporary result index.

**Why this priority:** It helps larger game/app collections, but the current catalog is small and users already have submenus. The extra navigation/input surface makes it less urgent than remote editing or lifecycle feedback.

**Acceptance checks:** Test nested and cyclic submenus, duplicate names, hidden submenu openers, empty results, missing applications, and Back/focus restoration. Confirm that typing/filtering does not persist any layout mutation.
